# 发布网页到 OpenAI 提供的域名：ChatGPT Sites

核实日期：2026-11-02。官方创建流程已重新读取，并实际检查 Sites 管理入口：内置浏览器需要登录；当前 Chrome 的已登录会话访问管理入口返回 ChatGPT 首页，菜单未列出 Sites，@Sites 未出现可选工作流。此账号可用权限仍待确认，尚未部署。

当前工作按现有 Vite 前端打包适配，继续使用 Supabase，以减少数据迁移。可交付包是前端源码与可重新生成的构建，不包含个人菜谱导出或认证凭据。实际 Sites 工作流须完成兼容性检查，再返回生产 URL；仅本地 build 成功不能确认可部署。

网页版入口是官方创建文档提供的 https://chatgpt.com/sites。当前 Codex 工具未提供独立 Sites 发布接口，官方说明 CLI/IDE 也不能独立管理 Sites，需要可用的 ChatGPT 网页或桌面工作流。

OpenAI 现在提供 **ChatGPT Sites**，可在 ChatGPT / Codex 中构建、托管、分享网站，也可检查并适配已有项目。发布成功后会返回生产 deployment URL；具体默认域名以实际部署结果为准，本文没有从已阅读的官方 Learn 文档确认固定后缀。使用者自有域名也可在功能可用时接入。官方文档未提供任意申请 `openai.com` / `chatgpt.com` 子域名的流程。

不是给我账号密码就能自动拿到一个域名。请本人在可用 Sites 的 ChatGPT / Codex 登录；是否能创建和公开发布取决于账号、套餐、功能开放进度及工作区权限。API key 不是 Sites 发布凭据。

## 当前项目适配路径

最小迁移方案：保留本点菜本前端和 Supabase 数据库，使用 Sites 兼容的部署流程托管网页。这样不必先迁移菜谱数据。Vite 已产生 `dist/` 静态产物，但这并不等于已经获得 Sites 兼容性认证，实际须由 Sites 工作流检查并适配。

另一方案：按 Sites 推荐 starter 重建数据层，把结构化菜谱放到 Sites 的 D1 数据库，文件放到 R2，并添加 Sign in with ChatGPT。官方明确区分了保存站点版本与保存访客数据；仅发布 HTML 或保存版本不会自动把本地菜谱变成云数据库。D1 持久化也不代表天然具备 Supabase 的 Postgres Changes 实时协议，需另外实现并验证刷新 / 同步行为。

## 可执行步骤

1. **打开 Sites。** 登录 ChatGPT 网页或桌面端，使用包含「website」的描述或 `@Sites` 进入工作流；在 Codex 中使用已有项目也可发出 Sites 部署请求。
2. **提供项目。** 打开本点菜本源码目录，或向对应 Sites 工作流提供项目文件；不包含 `node_modules`、`.git`、账号配置、私钥或个人数据导出。
3. **先检查兼容性。** 使用下面的提示词，先保留一个可审阅版本。
4. **选择数据方案。** 优先保留 Supabase；若迁移 D1，先导出个人菜谱，再明确用户隔离、唯一菜名、事务计数和历史记录迁移规则。
5. **完成预览验收。** 实测新增、编辑、重名、评分、刷新持久化和手机布局；若使用云端，验证多账号隔离和跨设备更新。
6. **确认访问范围。** 个人使用可保持仅自己 / 邀请访问。若要任何人打开网页，选择账号实际提供的公开访问选项；站点公开与菜谱数据权限是两个独立控制。
7. **部署并获取真实链接。** Sites 给出的 deployment URL 就是生产部署；保存版本而不部署可用于先审阅。
8. **更新登录回跳。** 若保留 Supabase，把 Sites 实际完整网页地址加入 Supabase Redirect URLs；每个新域名都是独立浏览器存储空间，需重新配置项目或导入本地备份。
9. **核验实际地址。** 在实际返回的生产链接打开，不把预览地址、聊天分享地址、源码仓库地址当成部署成功。

## 可直接使用的提示词

```text
使用 Sites 检查并准备发布这个个人点菜网页项目。
先检查项目能否生成兼容部署产物，必要时做适配；先保存可审阅版本。
保留分类、菜名去重、新增编辑、食材、调料、分步方法、制作次数、评分、今日菜单和采购清单。
优先保留 Supabase 数据层，按已登录用户隔离；不要自动把公开站点变成公开菜谱数据库。
不得把密码、service_role key、微信 AppSecret 或个人菜谱导出放入公开产物。
通过预览和实际数据验收后，再按我选择的访问范围部署，返回真实 deployment URL。
```
